# Cribrum — Design Document

- **Status:** Draft
- **Last updated:** 2026-11-04

## 1. Problem

A phone accumulates thousands of images. Many have no lasting value: blurry shots, near-identical bursts, lower-resolution copies of the same photo, pictures of lecture slides or homework taken for a single moment, screenshots, and forwarded media. Messaging apps make it worse. WhatsApp alone keeps received, sent, and status media in several folders, some of them hidden from the gallery.

Gallery apps are built for browsing, not for cleanup. They don't search the whole storage, and they can't tell a memory from clutter.

## 2. Goals and non-goals

### Goals

- Find **every** image on local storage, including folders hidden from the gallery.
- Detect images that are likely deletable, grouped into understandable categories.
- Make reviewing hundreds of candidates fast.
- Never delete anything without explicit confirmation, and keep every deletion reversible for a while.
- Keep the code modular, so detectors, image sources, and model runtimes can be swapped or added easily.

### Non-goals (for now)

- Cloud photo libraries (Google Photos and similar).
- Cloud-based classifiers.
- Publication on the Play Store.
- iOS and desktop versions.
- Visual polish beyond a clean, functional UI.

## 3. Key decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | **Android first, native Kotlin + Jetpack Compose.** | The heavy work is platform-specific: file system access, permissions, background jobs, image decoding, on-device ML. Cross-platform frameworks (Flutter, React Native) would still need native modules for all of it, plus a bridge layer that is hard to debug. Compose Multiplatform keeps a desktop option open. |
| D2 | **Python lab as the reference implementation.** | Detectors are built and tuned in Python on real photos first, then ported to Kotlin. Golden test fixtures check that both implementations give the same results. |
| D3 | **On-device analysis only.** | Privacy, zero cost, works offline. Cloud classifiers were evaluated (cheap, roughly $1–2 per 10,000 images) and postponed. The architecture keeps them pluggable (see §7). |
| D4 | **Recall over precision.** | Missing a deletable image is worse than surfacing one the user wants to keep. Thresholds start low, any single detector can make an image a candidate, and protection signals only lower an image in the ordering, never remove it from the candidates. The user can raise the thresholds in the settings (§6.1), which trades recall for a shorter review. |
| D5 | **Photo age is not a deletion signal.** | An old photo may be old precisely because it survived earlier cleanups. Per-image review state replaces age (see §6.3). |
| D6 | **Nothing is deleted without confirmation, and deletions go to a trash first, kept 30 days by default.** In the review, the main button with its counts ("Trash 45, keep 3") is the confirmation of a page: it applies the page at once, and the 30 day trash and the Undo snackbar make it reversible. Only a page that marks a favourite asks first, in a dialog (#321). Deleting for good, from the trash, always asks. | Mistakes must be recoverable. How long is a user setting. A dialog on every page repeated the button's numbers on a reversible action, cost a tap per page, and taught users to tap through dialogs, which made the one that matters, for a favourite, easier to miss. |
| D7 | **Personal, sideloaded distribution first.** | Allows the "All files access" permission (`MANAGE_EXTERNAL_STORAGE`) without Play Store review. |
| D8 | **Local images only.** | Cloud libraries need their own cleanup, but they are a separate, future problem (see §11). |

## 4. Finding images on Android

Two layers:

1. **MediaStore**, Android's media index. It covers the gallery and `Android/media/com.whatsapp/WhatsApp/Media/...`. It does **not** index folders containing a `.nomedia` file, such as `WhatsApp Images/Sent`. That is exactly where clutter piles up unseen.
2. **Deep scan** with `MANAGE_EXTERNAL_STORAGE`: a file system walk of shared storage that finds every image file, `.nomedia` folders included. The deep scan skips `.trashed-*` files (the system trash, which MediaStore hides by default) and `.pending-*` files (still being written), in both the lab and the app. It also skips `Android/.Trash` at the root of each volume, which is Samsung Gallery's own recycle bin: those images are already deleted as far as the user is concerned, and moving them breaks the Gallery's restore. Images already indexed there leave the index at the next scan, like any file the scan no longer finds, except those in Cribrum's trash. Since Android 11, `Android/data` and `Android/obb` stay inaccessible even with this permission. The deep scan recognises an image by the head of the file, except a file the index already holds with the same path, size and mtime: it does not read its head again. The walk also remembers the files it sniffed and found not to be images (the `not_images` table, with path, size and mtime), and does not read their head again either. On a phone most of the files the walk lists are not images, so without this every scan opens all of them. A file with a new size or mtime is sniffed again, whichever of the two lists held it, so a non-image that becomes an image with a new mtime is found at the next scan. Three cases get through that the head would decide differently: a non-image written over an image that kept its size and mtime, an image written over a non-image that kept its size and mtime, and a file MediaStore listed that the walk never sniffed (a DNG, BMP or TIFF), if MediaStore later drops it, for example because a `.nomedia` file appeared in its folder. The first and the third stay in the index until the size or mtime changes. The second stays out of it for as long. The app does not handle any of them. A change that lets the head accept more, such as a new format or HEIF brand, would leave every file of that kind already in `not_images` unfound, while a fresh install would find it, so that change must empty the table: a Room migration that runs `DELETE FROM not_images` on Android, a schema bump in the lab. The table has no version column. The walk reads the remembered files once, before it starts, and adds the ones it sniffs in batches of 300. It drops a remembered file it no longer finds only under a root it listed in full, like the index does for images, so the table does not grow without bound and an absent volume keeps its rows. The review reuses its ranking while the index version is the same. A write to `not_images` leaves that version alone, because no image changes with it. The walk records the files it finds in transactions of 300. A scan that stops partway leaves out the batch it was filling, and the next scan records those files again.

A pass forgets a file the scan no longer finds only when the file is under a volume the scan walked in full. A source reports the roots it listed, and a volume that is absent, such as a removed SD card, or a root with a folder that could not be listed is not walked: its rows keep their review state until a pass walks it again. MediaStore walks no folder, so it never makes a file gone, and it leaves out the same trash, pending files and folders as the deep scan.

Deep scan is the default (D7). The scanner merges both layers and identifies each file by its path, size, and modification time. A review decision follows the path, so a file that is moved or renamed is a gone row and a new one: it loses "keep" and is analyzed again, embedding included. Carrying the decision over would need a match by size, mtime and content hash inside the forget step, for a case that costs the user one more look at the image.

Indexing is incremental. The first pass processes every file, and later passes only process new or changed files. On Android, WorkManager runs a pass once a day at night while the phone charges, and whenever the user starts one with "Scan now". Opening the app starts no scan, since a pass keeps the CPU busy for minutes and the user who opens the app only wants to review. The first pass after install is the user's too: while the index is empty, the home screen says so and points to "Scan now", a filled button until the first scan, outlined after it with the date and time the last scan ended beside it ("Last scan: Nov 4, 03:12"). A pass already running keeps running when the app opens, and its progress shows, whether the nightly request or "Scan now" started it. "Scan now" is offered only while no pass runs. The daily request needs charging and a battery that is not low. WorkManager has no time-of-day constraint, so the first run is delayed to the next 02:00 local time. WorkManager measures each later run from the end of the previous one, so a night without charging would move the scan to the hour charging starts, say 14:00 at a desk, and every day after. Two rules keep the scan at night. The nightly worker scans only between 00:00 and 06:00, and outside that window it returns without scanning. When it ends, whether it scanned or skipped, it pins the next run to the following 02:00 (`setNextScheduleTimeOverride`). So a night without charging is skipped and the next 02:00 is set again. Only one scan runs at a time: a nightly run that starts while a "Scan now" pass is running returns without scanning. A scan does not run while a compression batch waits or runs either (§9). `setRequiresDeviceIdle` would also work, but it can hold a run back for days on a phone that is never idle while charging, and the delay is simple to test. A pass runs as a foreground service with a notification, since a first scan of thousands of images outlasts the few minutes Android gives background work. If Android refuses to start the foreground service from the background (such as ForegroundServiceStartNotAllowedException on Android 12+), the worker logs the refusal and continues as a standard background job under JobScheduler constraints, relying on the index to resume where it left off on subsequent runs. The notification title names the phase the pass is in ("Looking for images", "Reading the images", "Analyzing the images", "Comparing the images", "Classifying the images", then "Finding duplicates and bursts" for the group detectors) behind its number ("Phase 3 of 6 · Analyzing the images"), and its text shows the count. The scan screen names the phase the same way, with the number on its own line above the title. Joined to the title, the Italian line runs past 60 characters and is likely to wrap on a narrow phone, and the list below would then jump at a phase change. The total is a fixed 6, one for each title, numbered in the order the phases run: the walk, the metadata, the detectors that read no embedding, the embeddings, the detectors that read it, then the group detectors, which are all phase 6 even though each reports its own step. A rescan skips a phase that has no work, so the number can jump, from 2 to 6 for example. The total is not computed from what the pass will run, since that is not known when it starts. The number comes from the same mapping as the title, so the two cannot disagree. The phases follow the pipeline order in §7: the detectors that read no embedding run first, so the home screen has candidates after a few minutes instead of after the embeddings. The home screen reloads its list at each phase, so a user who watches the first scan sees them. The title changes as soon as the phase does. The count in the app updates at most five times a second, so the walk's count climbs instead of jumping, and the one in the notification at most once a second. Under the count, the home and the notification show the time left of the current phase, rounded to the minute ("About 12 min left in this step", "Less than a minute left in this step"). It is the phase's items left times its cost per item over the last 30 seconds, so a phone that slows down from heat, battery saver or another app raises it, and the 30 seconds keep it from jumping at each update. Nothing is carried from one phase to the next: it starts again at every phase, as the bar does, and the user sees how long the phase named above it needs, not the whole scan. An estimate of the whole scan was tried first (#242) and dropped (#271). It scaled the later phases by the current phase's live cost over a cost stored for it by the last scan, and a phase has no single cost per item, since the pipeline runs only the detectors an image is missing, so an item is one cheap detector or the whole set. A scan that repeated one cheap detector could store a tiny cost, and the next full scan would divide a normal live cost by it. That is the likely cause, read from the code and not measured, of the more than 8 hours the home once showed for a scan that took about 20 minutes. The price of the phase estimate is that the time can rise when a slower phase starts, and the user cannot read the length of the whole scan from it. There is no estimate during the walk, which has no total, nor for a group detector, which reports one item, nor in a phase before it has five seconds of samples; the line stays in place and is empty. The estimate is display only: it changes nothing the scan does, and costs a clock read and some arithmetic per progress report. The app also says when the phone is hot enough to slow the scan down, in one line under the progress with a thermometer icon: "The phone is hot, so the scan is slower", at the moderate and severe levels below, and nothing at the others (#321). It used to show every level with the headroom as a percentage ("moderate · 12%"), which a user cannot act on. The line comes last, so it never pushes the progress down when it appears. It reads the thermal status of `PowerManager` and its thermal headroom, and takes the worse of the two, because each covers a weakness of the other: some devices always report a status of none, and one headroom value can mean a different status on another model, while the headroom needs at least 10 seconds between reads and returns NaN otherwise. Headroom maps to a level with Google's scale (about 0.85 is light, 0.95 moderate, 1.0 and above severe); the status levels critical, emergency and shutdown count as severe, so there are four levels: normal, light, moderate, severe. A headroom that is not above 0 counts as no reading, and the last good one is kept, even across an unfold or a rotation, which recreate the activity, since a read soon after the last can return NaN on a phone that supports it. It is forgotten 10 seconds after a scan ends, so the next scan cannot open on an old reading. A listener and one loop, off the main thread and at most once every 10 seconds, run only while the home shows a running scan. The line only informs: it changes nothing the scan does, and the notification does not show it. Nobody has checked yet what a Galaxy reports for these two APIs. The index keeps what each pass did, so a stopped pass resumes where it was.

## 5. Detectors

Each detector looks at an image (or at the image index) and emits **signals**. No detector decides on its own whether an image should be deleted.

| Category | Technique | Notes |
|---|---|---|
| `EXACT_DUPLICATE` | Group by file size, then content hash (xxHash) | Exact, cheap |
| `NEAR_DUPLICATE` | Perceptual hash (pHash/dHash) + embedding similarity | Catches recompressed and resized copies, such as those made by WhatsApp. Suggests keeping the best copy: highest resolution, least compression, original EXIF metadata. |
| `BURST` | Capture-time clustering + embedding similarity | Suggests the best shot: sharpness, eyes open (face detection). |
| `BLURRY` | Variance of the Laplacian on a downscaled grayscale image | Measure the subject region when one is found, to avoid flagging portraits with an intentionally blurred background. |
| `BAD_EXPOSURE` | Luminance histogram | Pocket shots, black frames, blown-out frames |
| `SCREENSHOT` | Path and file name, image size equal to a screen resolution, no camera EXIF | Nearly deterministic |
| `DOCUMENT` | Text coverage (PP-OCRv4 text detection) + MobileCLIP zero-shot classification | Slides, whiteboards, handwritten notes, homework, receipts, printed pages. Only detection runs: how much text there is matters, not what it says. |
| `FORWARDED` | Messaging-app folder, missing camera EXIF, meme/sticker zero-shot prompts | Forwarded memes and greeting images |
| `STICKER` | The file is in a messaging app's sticker folder (`WhatsApp Stickers`, `WhatsApp Backup Excluded Stickers`) | Nearly deterministic. On the first phone, 62% of the images were stickers. |

### Order and stickers

The detectors that read no embedding run first (`BLURRY`, `BAD_EXPOSURE`, `SCREENSHOT`, `FACES`, `STICKER`), with the perceptual hash. Then the embeddings are computed, then `DOCUMENT` and `FORWARDED`, which read them, and last the group detectors (§7). On the first phone's index (11,308 images) the sticker folders held 6,056 of them, and `STICKER` and `SCREENSHOT` made 6,847 of the 8,132 candidates, so most candidates are there before the first embedding.

**Real images go before stickers.** The metadata step and the detectors that read no embedding take the real images first and the stickers after them, in both the lab and the app, so the candidates a user is looking for reach the home screen before the thousands of stickers. Only the order inside these two steps changes. Every sticker still goes through both, no result depends on the order, and the group detectors still get the images in index order. Stickers stay in the same steps instead of a phase of their own, which would change the phases the scan screen names. Two limits. Workers overlap at the switch, so the last real images and the first stickers run at once. An image that ran out of memory runs again after the queue is empty (§7), so a real image can come back after the stickers. The time left of the phase (§4) follows the images of the last 30 seconds, so it reads the real images' cost while the stickers are still ahead, and moves when they start.

**Neither MobileCLIP nor text coverage runs on a sticker.** An image in a messaging app's sticker folder is not embedded and `DOCUMENT` and `FORWARDED` do not run on it. The detectors that read no embedding, `FACES` (YuNet) included, still run on it. It would only have been listed under `STICKER` anyway (§8), so skipping these two models changes which other categories a sticker appears under, which the review already hides, not whether it is a candidate (D4). `STICKER` is still 1 for every sticker, so it keeps its place in the review order. The pipeline recognises a sticker with `isStickerFolder`, the rule the `STICKER` detector uses, so the two cannot disagree. This takes 6,056 of the 11,308 images off the embedding phase, 54%. A sticker embedding from an earlier scan stays in the index, but the pipeline does not read it, and the `DOCUMENT` and `FORWARDED` results an earlier scan stored for a sticker are dropped at the next scan, so a library gives the same result, reasons included, whether or not it was scanned before this rule.

**Groups still see stickers, by perceptual hash only.** `NEAR_DUPLICATE` links two images when their hashes are close or their embeddings are close, and `BURST` uses embeddings only to break a time chain, and only when both shots have one (§7, #108). A sticker with no embedding is linked by hash alone. No sticker on the index has a capture time, so none is in a burst, with or without an embedding. Both detectors already handle an image without an embedding, so neither changes and neither gets a new version. The cost is the groups that only an embedding made. On the same index 1,395 stickers are in a near-duplicate group when embeddings are used, 874 of them by hash too, so 521 leave their group entirely. They stay candidates under `STICKER`. A non-sticker whose only link was an embedding link to a sticker leaves its group as well: 2 did, both best copies of their group, and no candidate was lost. Embedding links are not kept for stickers because that is the 54% the phase would spend. The group fingerprint counts the embeddings, so it changes once on a phone that scanned before this rule and the groups are computed again. It also counts the stored perceptual hashes, so an image whose hash failed on one scan and works on the next is grouped again without waiting for another image to change. A content hash works another way, since the exact-duplicate detector computes it while it runs and only for files that share a size. The detector skips an image whose hash fails, and the run stores the paths that failed with its fingerprint. The next scan hashes those files again before it compares fingerprints: if one now reads, the detector runs, and if all still fail, it skips. So a file that can never be read does not make the detector run on every scan, and one that becomes readable is grouped at the next scan.

### MobileCLIP

[MobileCLIP](https://github.com/apple/ml-mobileclip) is a compact image–text embedding model that runs on phones. A single embedding per image, computed once and cached, serves three purposes:

- near-duplicate search (cosine similarity between embeddings);
- zero-shot classification against text prompts such as *"a photo of a projector slide"* or *"handwritten homework on paper"*;
- natural-language search later on.

With about 10,000 images, the embeddings take roughly 20 MB (512 float32 values per image), and comparing every pair directly is feasible without an approximate-nearest-neighbor index.

**Variant: MobileCLIP2-S0, as ONNX.** [MobileCLIP2](https://arxiv.org/abs/2508.20691) (2025) keeps MobileCLIP's architectures and improves their training: S0 goes from about 68% to 71.5% ImageNet zero-shot accuracy at the same size. S0 is the smallest variant (a 45 MB float32 image encoder), and its ONNX export ([plhery/mobileclip2-onnx](https://huggingface.co/plhery/mobileclip2-onnx), `onnx/s0/`, pinned to a revision) runs unchanged in the lab and in the app, on ONNX Runtime in both. Both compute the same embeddings, so golden fixtures can compare them directly. The export was checked against Apple's open_clip weights on the golden fixtures: image and text embeddings agree to within 1e-6. Input: shortest side resized to 256 px (bilinear), center crop to 256×256, RGB scaled to [0, 1], no normalization. Zero-shot uses the checkpoint's learned temperature, 64.33. The text encoder (254 MB) only turns prompts into embeddings. The lab computes those once into `lab/src/cribrum_lab/prompt_embeddings.json`, and the app build copies that file into its resources, so the text encoder never goes on the phone.

On the first phone's 912 labels, MobileCLIP2-S0 raised recall from 73% to 81% at the starting thresholds. With thresholds suggested for 80% recall, it flags 117 kept images instead of 146, for about the same number of candidates. Its similarities spread like MobileCLIP-S0's: at 0.90 it links 3,125 pairs of the 10,000 images against 2,905, so the NEAR_DUPLICATE and BURST thresholds stayed.

**License.** The MobileCLIP2 weights come under Apple's Machine Learning Research Model license, which allows research and other non-commercial use only. Cribrum is a personal, non-commercial app, so this is accepted. A commercial release would need another model, such as MobileCLIP-S0 (Apple sample code license) or Meta's Perception Encoder (Apache 2.0). The PP-OCRv4 text detector is Apache 2.0, which asks for the license text next to a redistributed copy. The pinned RapidOCR revision ships none, so the app does not package a notice yet: add PaddleOCR's license to the APK before any release.

On the dev machine (Ryzen 5 3600XT, CPU only), decoding and preprocessing take about 80 ms per image on one core (12 worker processes share it), and inference about 19 ms per image in batches of 16 on all cores: roughly 5 minutes for 10,000 images. These numbers were measured with MobileCLIP-S0, which has the same image encoder architecture (MCi0).

**In the app.** The build downloads the image encoder from the same revision, checks the same SHA-256 as the lab, and packs it in the APK's assets with Apple's license next to it. It is never committed. The app ports the lab's preprocessing step by step (Pillow's draft decoding, EXIF orientation, bilinear resize), and on the golden fixtures its embeddings match the lab's with a cosine of at least 0.99999. ONNX Runtime adds a 35 MB native library per ABI, so the APK only carries the arm64 one. On a Galaxy Z Fold7 (Snapdragon 8 Elite) the encoder takes about 47 ms per image on the CPU, the same at batch 1 and batch 16, and loading the model takes under half a second. A scan runs the encoder on the GPU, through ONNX Runtime's WebGPU execution provider, which the shipped ONNX Runtime build includes (#230). On the same phone that takes about 17 ms per image (batches of 16) and stays the same as the phone heats up, where on the CPU the time grows about 1.5 times. The embeddings match the CPU ones with a cosine of at least 0.999999. A phone or build without WebGPU runs the encoder on the CPU, and so does the rest of a scan once a run on the GPU fails, starting with the batch that failed: shaders compile, buffers are allocated and a device can be lost during a run, not only when the session is created. A crash inside the GPU driver kills the process and cannot be caught, which is an accepted risk. While the encoder runs on a batch, the next batch already decodes on the other cores, so memory holds at most two batches of pixels. An image that ran out of memory while decoding gets its retry alone, before the next batch starts. With the encoder on the GPU this made the embedding phase about a fifth faster (5.5 s against 7.1 s for 300 images, #229). On the CPU it made no difference, because the encoder and the decodes share the cores. The text model stays on the CPU with one thread per worker: its phase already keeps every core busy, and on the GPU it ran about a quarter slower. Preprocessing takes 30 ms for a WhatsApp JPEG, 53 ms for a 12 MP camera JPEG (draft decoding does most of the work) and 280 ms for a 1080×2400 PNG screenshot, which has no draft mode. With the encoder on the CPU, that puts a 10,000-photo library at roughly 15 to 20 minutes on one core, less with preprocessing spread across cores. A PNG or WebP has no draft mode, and a 4320×7680 one holds the bitmap, an equal `IntArray` and a float plane at once, about 12 bytes a pixel, which can exhaust the heap. So a non-JPEG image above 16 megapixels decodes with a sample size (a power of two, the smallest that fits, even when a side ends under the draft side, so a 1080×30000 scroll capture fits too), and below that limit it decodes at full size, so the pixels the lab compares against do not change. The golden fixtures stay below the limit. A wide gamut image (Display P3) keeps its stored values, because Pillow ignores the profile and `getPixels` converts to sRGB: on a saturated synthetic image the two embeddings differed by a cosine of 0.9993, under the 0.9999 the lab parity asks for. This changes the pixels, and so the embedding, perceptual hash, blur, exposure, faces and text results, of every wide gamut image (Display P3, Adobe RGB), but no detector version is bumped, as a deliberate exception to the bump rule: the gap is a cosine of about 0.9993 and only on that subset. Results already stored for such an image keep the sRGB-converted values until the file or a version changes. An image sampled this way has android pixels the lab does not reproduce, which only a huge PNG or WebP can reach.

**Text coverage in the app.** PP-OCRv4 detection runs on the CPU with one thread per image, as in the lab, so the scan's workers do not fight over cores. The build downloads the model from the lab's pinned URL and SHA-256 and packs it as a resource. Pillow's draft rule asks for both sides to stay at least 640 px, so a 1600×1200 JPEG decodes at full size, where MobileCLIP's 256 px draft decodes it at a quarter. That is why text preprocessing costs more than MobileCLIP's (about 65 to 100 ms against 31 for a 12 MP JPEG, and 80 to 115 ms against 14 for a WhatsApp one; PNG screenshots have no draft mode and cost the same, 110 to 175 ms against 117). On a Galaxy Z Fold7, with a release-like (non-debuggable) build and a warm runtime, detection plus preprocessing takes 150 to 240 ms per image on one thread, and the model alone about 100 to 150 ms. With one image per core (8 threads) it runs 20 to 26 images per second, so text coverage adds roughly 6 to 8 minutes to a 10,000-photo scan. Loading the model takes about 0.35 s. The speed tests must be run on such a build: a debuggable build runs the Kotlin preprocessing about three times slower, and the first rounds after install run slower again while the runtime compiles the hot loops. Hence `TextSpeedDeviceTest` warms up before it times, and the MobileCLIP times above, from a debuggable build, are about twice too high for preprocessing (14, 31 and 117 ms for the WhatsApp JPEG, the camera JPEG and the screenshot on the same build).

## 6. Ranking

### 6.1 Candidate selection

An image becomes a candidate if **any** signal exceeds its category threshold (D4). Thresholds are tuned in the lab for recall (§10), and the values are in `ranker.py` and `Ranker.kt`. Those values are the defaults. On Android the user can override the threshold of each category in the settings, except one whose detector scores only 0 or 1 (§8), and the app builds its `Ranker` from the defaults with the overrides on top. The signals are already in the index, so a change applies the next time a list is built and needs no scan. A threshold equal to its default is not stored, so a retuned default still reaches the user. The lowest value is 0.05, because a best copy of a group has score 0 and no threshold may suggest it (§7). Raising a threshold takes images out of the candidates, which is the one way the user can trade recall for a shorter review, so the screen says so. Protection weights are not part of the setting, and kept and trashed images keep their review state whatever the thresholds are. The lab has no overrides: it ranks with the defaults, so the two sides stay comparable. Images with the same likelihood are ordered by the xxh3 hash of their path, not by the path. File names such as `IMG_20190101_...` hold the date, so ordering by path would list the oldest photos first among equals, and photo age is not a signal (D5). The hash is arbitrary but stable, the same on both sides, and drops or adds no candidate.

### 6.2 Protection signals

These signals hint that an image is a memory: faces, favorites, membership in a user album, uniqueness (no near-duplicates). They lower an image's position in the review order but **never** remove it from the candidates.

They are ordinary `Signal`s whose category is a `Protection` (`FACES`, `FAVORITE`, `ALBUM`) instead of a deletable `Category`. They have no threshold, so they never make an image a candidate. The ranker multiplies an image's likelihood by `1 - weight × score` for each one. Uniqueness is not a signal: the ranker derives it from the image being in no duplicate or burst group. Candidates always stay ahead of the other images in the order. Favorites and albums only exist on Android (MediaStore), so the lab has no detector for them. Only `FACES` and `FAVORITE` exist so far: the ranker has a weight for `ALBUM` (0.6), but nothing emits it yet, so an image in a user album is not lowered.

`FACES` is an ordinary detector: it emits the signal, the index stores it, and its version applies, like any other signal. `FAVORITE` is not stored. The gallery changes it at any time, with no change to the file, so a stored copy would be stale as soon as the user hearts an image. `Review` asks MediaStore for the favorites each time it needs a ranking (one query for `IS_FAVORITE = 1`, a few dozen rows on a library of 1,000 images) and adds a `FAVORITE` signal of score 1 to those images in memory. The cached ranking is built again when the set differs, and the index and the detectors are not touched, so a scan has nothing to do for it. The same query runs again when the user applies a page. Reading `IS_FAVORITE` needs no permission beyond the one that reads the images, and `minSdk` 30 is where the column starts. An image the gallery hearted is still a candidate (D4): it only moves down the order.

**Trashing a favorite asks first.** The review marks a favorite with a heart (§8), and does not preselect it for the trash, even when it is a candidate: it stays in the candidates and in its place in the order, so recall is unchanged, but the user has to mark it. When the user marked a favorite on the page, the main button opens a dialog before applying it (D6), which says how many of the images are favorites, and its button reads "Move to trash anyway", in the error color. Cancelling trashes nothing. A page with no favorite marked applies at once, so trashing the similar copies of a favorite stays as quick as before, and a favorite the user kept on the page is not mentioned. The favorites the dialog named are the ones the page showed. If the gallery marks another marked image as a favorite while the page is open, applying finds it at that moment, trashes nothing, and shows the page again with the new heart and the marks the user had, so the next dialog names it. Faces come from [YuNet](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet), a 230 KB ONNX face detector under the MIT license. Like MobileCLIP, the same file runs on ONNX Runtime in the lab and in the app, so ML Kit is not needed for faces. The lab commits the file, and the app build copies it from there instead of downloading it.

### 6.3 Review state

Each image carries a review state:

- `UNREVIEWED`: candidate as usual.
- `KEPT`: the user reviewed it and chose to keep it. It is not suggested again unless a **new** signal appears. For example, a higher-resolution copy shows up and turns this one into the inferior duplicate. Keeping an image records the identity of each signal it has (category, group, role). Keeping also records which detectors had stored a result for it. The first result a detector stores for a kept image after that, such as `DOCUMENT` after a keep during the first scan, or a group detector on an image first seen in phase 1, is recorded as seen too: the image has nothing of that detector to be new against. Its later results count as before, so a group that forms or a role that changes after the first result is still new. A signal is new when its identity is not among the recorded ones: a newer detector version, a higher score or a retuned threshold is not new.
- `TRASHED`: in the app trash.

**Excluded folders** are a second user decision, kept apart from the review state because it covers a folder instead of one image. The index stores a list of folder paths. The ranker leaves out every image under one of them, like a trashed image, and so does the review screen: those images are in no category, no count and no group. The storage map leaves them out too (§8). Detectors still run on them and the index keeps their signals, so their duplicates still count and removing an exclusion brings the images back at once, without a rescan. An exclusion never touches a review state: nothing marks an excluded image `KEPT`, and nothing trashes it.

- An exclusion covers the folder **and its subfolders**. A folder is a subtree to the user (`Pictures/Family/2020` belongs to `Pictures/Family`), and excluding each subfolder by hand would be tedious. A sibling that only shares the name prefix (`Family2`) is not covered.
- A duplicate or burst group with a copy in an excluded folder is still offered for the copies outside it. The excluded copy is not listed in the group, so "keep best, trash the rest" never trashes it, and it is not marked `KEPT`. When the excluded copy is the best one, the group shows the other copies without it, and they can still be trashed, since the excluded copy stays as the survivor. A group whose only candidates are excluded is not offered at all.

### 6.4 "Review everything" mode

All `UNREVIEWED` images, ordered from most to least likely deletable. Going through all of them eventually brings false negatives to zero by construction. A missed image just shows up later in the order.

## 7. Architecture

The core idea is a pipeline of independent, interchangeable components.

```kotlin
interface ImageSource {                  // MediaStore + deep scan today; cloud libraries later
    fun scan(): Flow<ImageRef>
}

interface Detector {                     // one per technique; a cloud classifier would be one more
    val id: String
    val version: Int
    val category: Category? get() = null
    suspend fun analyze(image: ImageRef, context: AnalysisContext): List<Signal>
}

interface GroupDetector {                // duplicates, bursts: looks at all images at once
    val id: String
    val version: Int
    val category: Category? get() = null
    suspend fun analyze(images: List<ImageRef>, context: AnalysisContext): Map<ImageRef, List<Signal>>
}

enum class Role { BEST, INFERIOR }      // a group member's role, stored in evidence["role"]

data class Signal(
    val detectorId: String,
    val detectorVersion: Int,
    val category: Category,
    val score: Float,                    // 0..1
    val evidence: Map<String, String> = emptyMap(),
)

interface Ranker {                       // combines signals into candidates and an ordering
    fun rank(images: List<IndexedImage>): List<Candidate>
}

interface Trash {                        // app-managed trash, retention set by the user (30 days by default)
    suspend fun moveToTrash(images: List<ImageRef>): List<ImageRef>
    suspend fun restore(images: List<ImageRef>): List<ImageRef>
    suspend fun trashed(): List<TrashedImage>
    suspend fun purge(images: List<ImageRef>): List<ImageRef>   // returns what it deleted
    suspend fun purgeExpired(): List<ImageRef>
}

interface ModelRuntime                   // ONNX Runtime behind one interface
```

- Signals are stored with the version of the detector that produced them. When a detector improves, only its signals are recomputed.
- The pipeline runs in this order: scan, metadata, the per-image detectors that read no embedding (with the perceptual hash), the embeddings, the per-image detectors that read one, then the group detectors. Each step stores its results as it goes, so the home screen lists candidates from the first detectors on, and an interrupted pass resumes. Images in a sticker folder come after the real images in the metadata step and the first detectors, and skip the embedding and the detectors that read it (§5).
- A detector that reads embeddings says so (`usesEmbeddings`). That flag also puts it after the embeddings in the order above, so a detector that reads one without saying so runs before any exists. Its embedding lookup then throws something other than `MissingEmbedding`, so it lands in the run's failures on every pass instead of waiting for an embedding that its pass never gets. A result belongs to the embedding it read, so when the pipeline computes an embedding for an image it forgets that image's results from those detectors.
- A failed embedding is a failure of that image, not of the scan. The image gets no embedding, its failure goes into the run's failures, and the next run tries it again. An image that ran out of memory while decoding gets one more try alone, after its batch, since other decodes may have taken its memory. The scan always goes on to the detectors, so one bad file cannot keep DOCUMENT and FORWARDED from running on the others. The failures of the last finished run are kept for the settings screen (§8). A detector or a perceptual hash that runs out of memory while several images are analyzed at once runs again alone, after the others, and fails only if it fails then too.
- Detectors get per-image data they don't compute themselves (content hash, metadata, embeddings) through lookups in `AnalysisContext`. The pipeline backs them with the index, so each value is computed once and shared by every detector.
- Group detectors (duplicates, bursts) run over the index instead of over a single image. They use the same `Signal` output. Every member of a group gets a signal, with the group id in `evidence["group"]` and its role in `evidence["role"]`: `best` for the copy to keep (with score 0, so no threshold ever suggests it), `inferior` for the others. Images in no group get no signal.
- `NEAR_DUPLICATE` never links by hash two images whose pHash is 0 or has only the DC bit set. A uniform image gives one of the two, since every AC term rounds to 0: black hashes to 0 and any other flat image to the DC bit, so they all sit within a bit of each other. A few simple shapes, such as a white image with a dark band over its left or top eighth, give the same hash and are treated the same way. Such a member says `evidence["flat"] = "true"`. It can still join a group through its embedding, and a uniform image is also a `BAD_EXPOSURE` candidate either way.
- `BURST` chains shots by time and embedding, comparing each shot with the last shot of the current burst. When it does not follow, it starts a possible new burst, and if the next shot follows the last shot of the first burst instead, the shot between is dropped as one different frame. Without this, A, B (another subject), C (like A) would split into three singletons, and one different shot would destroy the burst. The 3 s gap is measured from the last shot of the burst, so shots 2 s apart can chain for longer than 3 s in total. The best shot is the sharpest by the BLURRY measure (the variance of its sharpest region), rounded to one decimal as `BLURRY` stores it in its evidence. The group phase reads that stored value instead of decoding every member of every burst again, and decodes a shot only when it has no `BLURRY` result, such as after a failed blur run. Rounding on both paths makes them rank shots the same. The group fingerprint includes the `BLURRY` detector's id and version, so a new blur version reruns the group detectors even when no file changed.
- The Python lab mirrors these interfaces one-to-one, so porting is mostly translation.

Coil draws each photo at up to 2,048 px on its long side, and once the zoom needs more than that, `TiledImage` decodes the part on screen again with `BitmapRegionDecoder`, cut into tiles of 512 decoded pixels, at the largest power of two sample that still gives each screen pixel at least one pixel of the file. Both layers share one `Zoom`, the same region and scale, and each reads its own file at its own resolution, so at the original's 100% a copy at Smallest shows its own pixels four times larger. The zoom goes up to twice the original's full resolution, so single pixels and JPEG blocks show, and the image's state description says it as a share of that resolution ("Zoom: 3% of full resolution" at rest on a 200 MP photo on the summary's slider, 100% at one screen pixel per pixel), for a screen reader: the line under the photos, the "Before and after" heading and the paragraph about the gestures left the screen in #321, and the gestures are in the image's description. A tile is read in the file's own pixels and drawn turned by the EXIF orientation, the same turns as `Imaging.transpose`. **One decode per view.** Since Android 7 a JPEG region decode goes through Skia's JPEG codec with no index of the file, so every `decodeRegion` reads every row above the region at full width, and a coarser sample saves only the inverse DCT. A region at the bottom of a 200 MP photo costs about a whole pass over the file, whatever its size. Measured in the review of #303 with libjpeg-turbo's crop on a synthetic 16320 × 12240 JPEG at quality 90, on one laptop core: one tile at the top took 29 ms, in the middle 300 ms, at the bottom 510 to 600 ms, and a full-width strip at the bottom the same as one tile. A full screen at 2 times, 30 tiles, took about 9.8 s read one by one and about 0.6 s as one call. So `TileLoader` reads the bounding box of a view's missing tiles in one decode and cuts it into the grid, and the box, which is never drawn, is recycled. A box over 100 MB of decoded pixels is read a row of tiles at a time instead, the row nearest the centre first, since a decode and its copies would hold twice the box; neither the panels nor a phone's full screen come near it. Only the tiles that cover the view are kept: each change of zoom or position drops the others (left to the garbage collector, not `recycle()`d, since the render thread may still draw the last frame) and decodes the missing ones off the main thread. When the zoom crosses a power of two, a tile of the old sample stays, drawn under the new ones, until the new tiles over it are in, so the base image never shows in between; that holds up to twice the tiles during the switch. The decoded pixels on screen stay under twice the view on each side, plus a tile at each edge: about 14 MB for a 500 × 375 px view, and about 75 MB for a full screen of 1080 × 2340 px, whatever the photo's size. The slider's layers are as wide as the summary, about 1,000 × 750 px on a phone, so each holds roughly 25 MB and the two 50 MB, scaled from the 14 MB figure by the area of the tile grid and not measured. Only the photo on screen has layers: a photo on another tab holds no tiles. These figures leave out the GPU's copy of each drawn tile, the box while it is cut and the tiles waiting for the garbage collector, so real use is about twice that. It still fits next to the preview's own encode of a 200 MP photo (1.44 GB at High quality on the Fold7, §9), and neither layer decodes a tile until every preview of the summary is made or has failed, so a zoom during an encode does not slow it, nor takes the memory its check counts on, and only the base image shows. With three 200 MP photos the user waits for all three encodes before the zoom shows real pixels. A view whose decode fails, out of memory included, drops all tiles and leaves the base image; the next change of zoom or position tries again. Leaving the summary cancels the tile work, waits for the decode in progress and closes the decoder, which held its own descriptor of the file: the preview file is closed a decode after it is deleted, not left open. `BitmapRegionDecoder` won over a library such as Telephoto (`zoomable-image-coil3`), which does subsampled tiles on top of Coil: it is in the platform, the two panels must share one zoom and keep the summary's own gestures (one finger at rest scrolls the summary), and #300's slider needs one source clipped to a region, which a `TiledImage` under a clip does. A library would bring its own gesture and state model to bend around all three. Robolectric checks the tile region, the orientation, that an original and its half-size copy show the same part of the photo, the zoom math, and the loader against a fake decoder: one decode per view, rows centre first, the old sample kept until covered, the retry after a failure and the close. It also decodes one real region. For the comparison it checks the choice of photos, that the previews run one at a time and in order, that the first shows before the others are made, that a refused one does not stop the rest, that closing stops the ones not started and that every file is deleted, the tabs and the descriptions that read their sizes, and the slider's gestures (the handle moves the line without panning a zoomed photo, a finger elsewhere pans or leaves the drag to the summary, a pinch with a finger on the handle zooms, the tick at each edge) and its semantics (description, range and the increment and decrement action). It cannot see the clip, so that the copy shows only to the right of the line is left to the phone. What it cannot check stays with the phone: how long a view takes on a 200 MP file (about one pass over the file down to the bottom of the view, so a view low in the photo waits longest, and a progressive JPEG has to be read whole for each decode, with memory for all of its coefficients, which a camera does not write but another app may), whether seams show between tiles, and how the switch from the base image to the tiles looks. A photo the compressor refuses at that level has no preview, and says so. The summary does not stop there: the batch refuses that photo again. The warning is the decision of #173 (§9), in the same type size as the rest of the summary: the date, the place and the camera details are kept, and it lists what is lost, naming for each loss the number of selected photos that have it from the flags the scan stored, and leaving a line out when no selected photo has it. The shooting mode info has no flag, so its line is always there. It ends by saying all of it comes back only by restoring the original from the Cribrum trash, within the retention in days. Confirming starts the background batch (§9, #287) and the page shows its state in place of the list, at the top of the page: waiting for a scan, with the scan's phase under it ("Phase 4 of 6 · Comparing the images"), "Compressing 3 of 12" with the saving so far and a note while the job pauses for heat, and "Stop compressing", which waits for the photo in progress; the line that says so shows only while a batch runs, since a waiting batch has no photo in progress. At the end it shows how many photos were compressed, the real saving, how many were left as they were for each reason, how many a stop kept the batch from reaching, how many compressed photos lost their favourite flag because the user declined the request to mark them again (§9, one line, absent otherwise), and one Undo that puts every original of the batch back from the trash. "Done" is the filled button and "Restore originals", the Undo of the batch, the outlined one after it (#321): it has its own words because in Italian "Annulla" is also the summary's Cancel, and undoing the batch is the rare choice. A snackbar with Undo, as in the review, was the other option, but the Undo can wait minutes for a scan and says so on the page, which a snackbar cannot hold. The Undo waits while a scan or a batch runs (§9), which can take minutes, so the page then shows a progress line saying so (read out by a screen reader), turns Undo and Done off, and ends with the list once the originals are back. The result lives in memory only, so a process that was killed mid-batch comes back to the list with no Undo, and the originals compressed so far are in the trash screen. - Candidates are grouped by category, and each group is sorted by confidence.
- The categories of one image per entry (`BLURRY`, `BAD_EXPOSURE`, `SCREENSHOT`, `DOCUMENT`, `FORWARDED`) can be grouped by date. ## 9. Deletion and trash

The system trash (`MediaStore.createTrashRequest`, Android 11+) only works for files MediaStore indexes, so it misses `.nomedia` folders. Cribrum therefore keeps its **own trash**: files move to an app-managed folder together with their original path, and are purged after a retention the user sets in the settings screen: 7, 14, 30, 60 or 90 days, 30 by default. One mechanism covers every file.

The trash is a `.cribrum-trash` folder at the root of each storage volume, with a `.nomedia` file so galleries skip it. Each trashed file gets its own folder there, holding the file under its own name and an `origin.properties` with its original path, size, mtime, the time it was trashed (`trashed_at`), when the trash first saw it (`seen_at`), and `favorite=true` when the gallery had the image marked as a favourite at that moment (see The favourite flag). Moving is a rename on the same volume: it is instant, and it keeps the mtime, so a restored file is the same `ImageRef` as before. Moving refuses a file named `origin.properties`. Because the trash lives on shared storage and needs no database, it survives an uninstall and can be restored by hand. A file that changed since its scan is not trashed, and a restore uses `Files.move` without replacing existing files so it cannot overwrite a file that took the original path. The trash is the only code that deletes files. The retention is read on every purge, not stored with the item, so a change applies to the items already in the trash too: lowering it purges what is now older than the new value at the next scan, so the settings screen first asks for confirmation, with the number of images that would go, when the new value would purge at least one. A purge needs the trash to have seen the item for the whole retention: both `trashed_at + retention` and `seen_at + retention` must be at or before now. Moving writes `seen_at` with `trashed_at`, and the purge writes it for items that lack one. When the system clock is before `seen_at`, the purge rewrites `seen_at` to now, so turning the clock back does not shorten retention. Reading a trash item treats a `trashed_at` in the future as now, and skips corrupted or truncated records without failing. The trash purges an item once both retention checks pass, or when the user deletes it for good from the trash screen.

The trash screen (#321) shows each image with its days left. A tap selects it, and a long press opens it in the same full size view as the review, with its folder, its days left and the heart of a favourite, so the user sees a photo before restoring or deleting it. Under the grid, Restore is the filled button. Deleting for good is a text button in the error color beside it, so it weighs less: "Empty trash" with nothing selected, and "Delete 3" for the selected images only while some are selected. The selection holds trash items, by their file in the trash, not original paths: an original and its compressed copy share a path, and so can a file trashed twice. `AppTrash.purge` deletes one item for each image it is given, so two items that are the same image go only when both are asked for. Its dialog says how many images it deletes and how much space that frees ("This frees 412 MB and cannot be undone."), with its confirm button in the error color, and the images go through `Review.purge`, the trash's own purge.

A trashed image stays in the index, as `TRASHED`, while its file is in the trash: the scan does not find it, but does not forget it either. Its signals and review state are still there if it comes back. The index forgets it when the trash purges it, if the delete worked and the row is still `TRASHED`: a failed delete keeps the row, and so does a new file now at the same path. A scan reconciles the two: a `TRASHED` row whose file is back on disk with no item in the trash, because someone moved it back by hand, becomes `UNREVIEWED` again, and one that is neither on disk nor in the trash is forgotten, as long as its volume was walked in full (§4). A file written at the path of a trashed image starts `UNREVIEWED` too. The scan judges only rows in the state they had when it began, so a review action that runs meanwhile, like a restore, keeps its result.

Compression (#173) rewrites a photo the user keeps, so it follows the same rule: the original goes to this trash. What it can rewrite, and how, was measured on a Galaxy Z Fold7 (One UI 9, SDK 37) in #283. Nothing was measured on Android 11 to 16 (SDK 30 to 36). Compression is Android only, so the lab has no counterpart.

- **Eligible photos.** A file is compressible when its bytes are an 8-bit baseline, extended or progressive JPEG (SOF0, SOF1 or SOF2, sample precision 8), it is not a Motion Photo, and nothing unknown follows the image (see Motion Photos). The phone had no SOF1 file, and Android does not decode 12-bit JPEG.
- **Ultra HDR.** A photo with a gain map is eligible only on API 34 and later, where `Bitmap` has the gain map API. Below that, `Bitmap.compress` writes a plain SDR JPEG. A file has a gain map when its headers have the `hdrgm` XMP or the ISO 21496-1 APP2 together with an MPF APP2. On SDK 37, `BitmapFactory` decodes the gain map, `inSampleSize` and `Bitmap.createScaledBitmap` keep it, and `Bitmap.compress` writes all three markers again (the `hdrgm` XMP, the ISO 21496-1 APP2 and the MPF APP2). The full pipeline ran on 2 photos. API 34 to 36 are untested, and so is whether the Gallery shows the result as HDR. The compressor refuses a photo whose headers show a gain map when the decoded or scaled bitmap has none, or when the headers of the copy it wrote do not show one, so an Ultra HDR photo never comes out as SDR. The second check covers an encoder that drops the gain map, which API 34 to 36 may do, untested. Ultra HDR photos are in because they are most of what is worth compressing: 195 of the 345 camera JPEGs on the test phone have a gain map, all 13 of 200 MP among them.
- **Motion Photos.** A miss destroys the video, and the test phone had no Motion Photo, so the rule is strict. A file is not eligible when any of these holds: its XMP has `MotionPhoto` or `MicroVideo` set to `1`, as an attribute or an element, under any namespace prefix; it ends in a Samsung SEF trailer (`SEFT` in the last four bytes) whose directory has a `MotionPhoto_Data` entry; its XMP `Container:Directory` lists an item whose semantic is neither `Primary` nor `GainMap`; or something other than an MPF secondary image or a SEF trailer follows the image. That last check covers other vendors' formats and Pixel portrait photos: with the SEF trailer cut off (from its first data entry to the end), the remaining bytes must end in an EOI (`FFD9`), and when an MPF lists secondary images, the last of them must end exactly there. An MPF whose entries do not parse fails this check, and a header walk that never reaches SOS (a broken segment, or more than 4,096 steps) makes the file unsupported, since a flag behind the break would go unread. The checks read the header segments, the file's last bytes and the SEF directory, never the image data. Bytes after the first EOI alone prove nothing: a gain map or a SEF trailer follows it in 196 and 330 of the 3,587 JPEGs on the test phone. On the first scan with these rules on the test phone, of 3,879 JPEGs, 3,865 were eligible (202 of them Ultra HDR), 12 were excluded for trailing data (1 of them Ultra HDR) and 2 were unsupported. The container and Motion Photo rules excluded none. Before the compress screen (#286) or the background job (#287) ships, the rule is checked on one Motion Photo taken on purpose.
- **What the result keeps.** The compressor copies every tag ExifInterface knows (154 tags in `androidx.exifinterface` 1.4.2, the GPS reference tags `GPSLatitudeRef`, `GPSLongitudeRef`, `GPSAltitudeRef`, `GPSSpeedRef`, `GPSImgDirectionRef` and `GPSDestBearingRef` among them, which `CompressorTest` pins, `GPSAltitudeRef` of 1 (below sea level) included), except the structural ones: the pixel size, the thumbnail and its offsets (with `Compression`, which in a JPEG's Exif describes the thumbnail), the tags that say how the original's pixels were encoded (`YCbCrSubSampling`, `BitsPerSample`, `PhotometricInterpretation`, `SamplesPerPixel`, `PlanarConfiguration`), which the new encode decides again, the TIFF strip and subfile tags and the raw formats' own tags (DNG, ORF and RW2), which a JPEG does not have, and the IFD pointers, which ExifInterface writes itself. It then sets the pixel size tags the original has to the new size. It finds the tags by reflection on ExifInterface's `TAG_` constants, which a ProGuard rule keeps in release builds, and refuses to compress if it finds fewer than 100. The maker note and tags ExifInterface does not know are not guaranteed. On 8 photos every copied tag read back the same, date taken, GPS, orientation, camera and lens included. The compressor keeps the XMP that `Bitmap.compress` writes, which for an Ultra HDR photo describes the new gain map, and does not copy the original's. One scratch copy got the same `DATE_TAKEN` from MediaStore as its original. That was not through the real swap, and Robolectric has no MediaProvider, so it is still to check on the phone after the real rename. The phone check on #285 found `GPSAltitudeRef` missing from the copies. ExifInterface 1.4.2 drops a tag at parse time when it is stored in a TIFF format other than the one it expects, and for this tag it expects BYTE or UNDEFINED: stored as ASCII, SHORT or LONG it reads as null, and so do its bytes and range. The phone stored it in one of those. So when ExifInterface returns null for it, the compressor reads tag 5 of the GPS IFD straight from the original's Exif APP1 (any of the five formats, either byte order) and writes 0 or 1 with `setAttribute`, with tests for SHORT, LONG, ASCII and big endian. The five other GPS reference tags (`GPSLatitudeRef`, `GPSLongitudeRef`, `GPSSpeedRef`, `GPSImgDirectionRef`, `GPSDestBearingRef`) expect ASCII (UNDEFINED passes too) and are dropped the same way when stored as BYTE, SHORT or LONG. No file seen does that, and a reference letter in a numeric format has no defined meaning, so they have no fallback.
- **What the result loses.** The compressed copy loses all of the original's XMP, except what `Bitmap.compress` writes for Ultra HDR. It also loses the Samsung SEF trailer, APP11 C2PA content credentials, any IPTC APP13, COM segments, the EXIF thumbnail, and any other data after the image end. The maintainer accepts that ([#173](https://github.com/Bert0ns/cribrum/issues/173#issuecomment-6591131814)), and the compress summary warns before confirming (#286). All of it stays only in the original, until the trash purges it. The warning says that the date, the place and the camera details are kept. It says what is lost: Samsung Gallery's Revert for an edited photo, re-blurring the background of a Live focus shot (its depth maps), the shooting mode info, the edits, ratings, keywords, captions and people tags that other apps saved in XMP, and C2PA content credentials, such as an "edited with AI" label. It also says that all of it comes back only by restoring the original from the Cribrum trash within the retention. The scan may store a flag per loss (re-edit data, depth map, XMP, C2PA) so the summary can name counts (#284).
- **Resolution.** The limits are 50,000,000 pixels for Balanced and 12,000,000 for Smallest. A photo already at or below the limit decodes at `inSampleSize` 1 and is not scaled. Otherwise the sample size is the largest power of two `s` with `ceil(w / s) × ceil(h / s) ≥ 0.99 × limit`. A test checks that rounding against a real decode. If the decoded bitmap is still above the limit, it is scaled to `floor(w' × f) × floor(h' × f)`, with `f = sqrt(limit / (w' × h'))` and `w' × h'` the decoded size. The 1% is there because half of a 200 MP photo is 49.9 MP. Without it, Balanced decodes all 200 MP: 1.0 GB and 3.3 s instead of 0.37 GB and 1.3 s. A megapixel is 10^6 pixels, so the Fold7's own 12 MP (4000 × 3000) and 48 MP photos keep their size at Smallest and Balanced. The table is #285's test:

  | Original | High quality | Balanced | Smallest |
  |---|---|---|---|
  | 16320 × 12240 (200 MP) | as is | `s` 2, 8160 × 6120 | `s` 4, 4080 × 3060, scaled to 4000 × 3000 |
  | 12000 × 9000 (108 MP) | as is | `s` 1, scaled to 8164 × 6123 | `s` 2, 6000 × 4500, scaled to 4000 × 3000 |
  | 8192 × 6144 (50.3 MP) | as is | `s` 1, scaled to 8164 × 6123 | `s` 2, 4096 × 3072, scaled to 4000 × 3000 |
  | 8000 × 6000 (48 MP) | as is | as is | `s` 2, 4000 × 3000 |
  | 4000 × 3000 (12 MP) | as is | as is | as is |

- **Memory.** Bitmap pixels live in native memory, so the 512 MB Java heap is not the limit. On the Fold7, High quality on a 200 MP photo peaked at 1.44 GB of native memory and 13 MB of Java heap. The peak was 1.8 times the decoded bitmap, for both the 200 MP and the 48 MP photos. Before each photo, the compressor estimates the peak as 2.5 times the decoded bitmap, `ceil(w / s) × ceil(h / s) × 4` bytes with the dimensions after sampling. It reads `ActivityManager.getMemoryInfo` then, not once per batch, and the photo fits when the estimate is at most `availMem − threshold`. The factor 2.5 leaves about 40% over a single phone's measurement. On the Fold7, with 2.7 GB free, High quality on 200 MP (an estimate of 2.0 GB) passes. The large decoded bitmap is recycled as soon as it is scaled. A photo that does not fit is refused at that level, with a message that the phone has too little free memory for it, and an `OutOfMemoryError` during the decode, the scale or the encode is a refusal too. High quality never falls back to a smaller size, because it promises the original resolution. On the Fold7's sensor sizes only High quality reaches gigabytes, but a 64 or 108 MP photo from another phone decodes at full size at Balanced too, then scales, and can hit the check. The free memory reading is injected, so tests can fake a low-memory phone.
- **The marker.** The marker is an APP15 segment: the identifier `cribrum` and a NUL byte, then plain ASCII `key=value` lines ending in `\n`, with no comment or date line (`Properties.store` adds both, so the writer does not use it). The keys are `version=1`, `level` (`high`, `balanced` or `smallest`) and `compressed_at` (ISO 8601, UTC). It takes about 70 bytes. A reader takes the first APP15 segment before SOS whose payload starts with `cribrum\0`, wherever it sits, and ignores any other APP15 (GraphicConverter's starts with `Q`). The compressor writes the marker last, after the EXIF save, then sets the mtime. It goes directly after the Exif APP1. With no Exif APP1 it goes directly after SOI, or after an APP0 JFIF that follows SOI. Either way it stays before the MPF APP2. MPF gives the gain map's offset from its own segment, so a segment between the MPF APP2 and the gain map image moves the gain map away from where MPF says it is. The size MPF records for the primary image goes stale by the length of the EXIF and the marker. Android's decoder ignores it and found the gain map, so #285 leaves it. ExifInterface saves keep the marker byte for byte (one moved it behind the XMP APP1, still before MPF), and BitmapFactory, ImageDecoder, ExifInterface and MediaStore ignore it. APP11 was the first candidate, but it belongs to JUMBF, which C2PA content credentials use, and the camera had already written C2PA into two photos. APP15 appears in none of the 3,587 JPEGs. Whether the Gallery, sharing or a cloud backup keeps the marker was not tested, and a file that loses it counts as not compressed (#173).
- **What the scan reads (#284).** The metadata phase (phase 2) reads these rules for every image whose header gave `image/jpeg`, as a second step after the metadata (`jpeg_headers`), and keeps how long it took as the `jpegHeaders` phase time. It stores the result in a `jpegs` table, one row per JPEG: the rules' version, the first rule the file fails in the order above (`unsupported`, `motion_photo`, `sef_motion_photo`, `container`, `trailing_data`) or `eligible`, whether it has a gain map, the estimated quality, the marker and its keys, and the four loss flags. The API 34 rule is applied when the list is read, not stored, so a phone updated to API 34 lists its Ultra HDR photos without a rescan. A changed file loses its row and is read again, a forgotten image loses it with the image, and a new rules version reads every JPEG again. Version 5 of the index adds the table and starts empty, so the first scan after the update reads every JPEG, as a fresh install does. The table is Android only, so `IndexSchemaTest` leaves it out of the comparison with the lab's schema. A write to it leaves the index version alone, as `not_images` does, since no ranking changes with it. The read keeps only the first 32 bytes of an Exif APP1 or an ICC APP2, whose contents no rule needs, since a camera's Exif with its thumbnail runs to about 64 kB, and it gives up on a SEF directory of more than 1,024 entries. On synthetic files of 200 kB (an Ultra HDR file with a SEF trailer), on the dev machine with the file in the page cache, a read takes about 0.26 ms. On the test phone, the first scan after the update read the headers of 3,879 JPEGs in 6,360 ms, about 1.6 ms a file, in a scan of 11.5 s. After each scan, the log tag `jpeg-status` gives the number of JPEGs per status, with and without a gain map, for the check on a real library. A failed read is a failure of the `metadata` step, and the next scan reads the file again. The re-edit flag is a SEF entry named `PhotoEditor_Re_Edit_Data` and the depth map flag one whose name starts with `DualShot_DepthMap`, the names found on the lab's copy of the test phone. XMP is any XMP APP1, and C2PA an APP11 whose payload starts with `JP`.
- **Quality and saving estimate (#284).** The quality is ImageMagick's estimate from the quantization tables. Its hash and sum tables are the standard tables scaled at each quality, so the app computes them. On JPEGs that Android's own encoder wrote at eight qualities from 30 to 100, it gives back the quality they were written at. The bytes a level would leave are the file's size, times the share of pixels the 1% rule keeps, times the size of a JPEG at the level's quality over its size at the file's estimated quality, from a curve measured in the lab with Pillow's libjpeg-turbo, times 0.934, the median ratio of Pillow's file at the original's estimated quality to the camera's own file. On 12 camera photos in the lab (6 of 12 MP, 3 of 48 MP, 3 of 200 MP, estimated at 92 to 96), the estimated saving was off by a median of 0 points of the original size at each level, and by 16 to 20 points at worst. For the 200 MP photos the estimate is within 5 points of what #283 saved on the phone. It is a lab calibration against Pillow, not against `Bitmap.compress`. A level whose estimate is not smaller than the file shows as saving nothing.
- **The swap.** The compressor writes the copy next to the original, on the same volume, as `.pending-cribrum-<random>.jpg`: the scan skips it (§4), and moving it to the original's path is a rename. It copies the EXIF, writes the marker, then sets the copy's mtime to the original's, before the swap. A rename keeps the mtime, so the copy has it from the moment it takes the path. Then `AppTrash.replaceWithCopy` moves the original to the trash, with the copy's size and mtime in its `origin.properties` (`compressed_size`, `compressed_mtime_ns`), renames the copy to the original's path without replacing any file, and tells MediaStore about the path. A copy that is refused or never takes the path is deleted by `AppTrash.discardCopy`, which deletes nothing but a file with exactly that name, outside the Cribrum trash, so the trash is still the only code that deletes. If the original changed since its scan, its record cannot be written, or anything throws before the swap, nothing moves and the copy is discarded. If the copy cannot be renamed, the original moves back. If that fails too, the original stays in the trash, where a restore puts it back: the compressor says so with its own reason, and marks the row `TRASHED` like any trashed image, so the next scan does not forget it. Once the copy has the path, the compressor reports it done even if the index update after it fails, since the next scan records the copy. A process killed between writing the copy and the swap leaves the hidden copy next to the original. The scan skips it, and the next batch discards it (see the batch job below). A process killed after the original went to the trash and before the copy took the path leaves the path empty, under a row that is not `TRASHED`. The scan keeps such a row while the row still holds the original's size and mtime and the trash holds that original with a compressed copy, so a restore finds the row with its review state, as after a finished swap. After a finished swap the row holds the copy's size and mtime, so a copy deleted in another app leaves the index like any gone file. A scan that cannot list the trash forgets no row, since any missing file could be such a half swap.
- **Restore.** Restoring an original whose record names a compressed copy first moves the file at its path to the trash, as an ordinary item, if it is still that copy (the same size and mtime), then moves the original back. A file at the path that is not the copy, such as one the Gallery edited, is left alone and the original stays in the trash, as with any restore onto a taken path. If the original cannot be moved back, the copy returns to the path. The copy's item is purged like any other, and purging the original's item leaves the copy where it is. Nothing is deleted outside the trash, so a compression can be undone for the whole retention (D6). A restore also marks a favourite again (see The favourite flag).
- **The index.** The index has one row per path (§4), so the copy takes over the original's row. `ImageIndex.record` sees the new size, keeps the review state, and drops the metadata, hashes, embedding, signals and `jpegs` row, which the next scan computes from the copy. The copy has the marker, so once the scan reads it again the compress page shows it as compressed. Signals are not carried over: the content hash changes, and at Balanced and Smallest so does the resolution that picks the best copy of a group. A kept photo stays kept, and a new signal on the copy, such as a group role that changed, brings it back as for any edited file (§6.3). The original's trash item has no row. Restoring it puts the row back to the original's size, which drops the copy's `jpegs` row, and the row is analyzed again. It keeps the review state it had, because a restore is a keep decision and the row still holds the original's kept signals and detectors, which a changed size does not drop. This is the one restore onto a row that is not `TRASHED`. Any other restore onto a row that changed since the trash took the file still comes back unreviewed (`Review.restore`). Purging either item never forgets the row while the copy is at the path, since the row is not `TRASHED`. When the user trashes the copy too, both items hold the path and the row is `TRASHED`, so a purge forgets the row only when no item left in the trash holds its path (`Trash.unheldPaths`, used by the purge from the trash screen and by the scan's purge of the expired items). No migration.
- **The favourite flag (#288).** MediaStore keeps `IS_FAVORITE` on a row, not on the file. Where a compression or a restore keeps it:
  - *The swap loses it.* The copy is a new row (new `_id` and `date_added`, #285), so the gallery's heart is gone.
  - *Undo on the test phone kept it.* The original goes to `.cribrum-trash` and back by rename, and the phone brought its old row back (#285). The code cannot rely on that: a MediaStore scan that drops the row while the file sits in a `.nomedia` folder would leave the restored file with a new row and no mark, and nothing in the app can tell which phones do that. So the trash writes `favorite=true` into the item of every file it moves (the swap's original and an ordinary trashing alike) when MediaStore flags its path at that moment. The query names the paths it asks about (`DATA IN (...) AND IS_FAVORITE = 1`, 500 at a time): the paths of a move call, or the one path of a swap, never every favourite of the library for each photo. A query that fails counts as none, so it never stops a move. A copy that a restore puts in the trash is recorded the same way.
  - *The batch.* The swap reports whether the original was a favourite, and the batch keeps the paths of the compressed ones (`BatchResult.favorites`). After the result is published, the job asks for the mark on those paths in one request. The request is dropped, when it is queued and again when it is about to launch, if that result is no longer the one on show (the user undid the batch, or started another): the copies are in the trash then. A photo whose compression was refused or stopped still has its own row and mark.
  - *A restore* (Undo of a batch, the trash screen, Undo of a review) asks for the mark on the restored files that were favourites, after the restore. In both cases the request runs on the app's own scope after the restore or the batch has returned, so the restore, the Undo and the scan lock never wait for it: it waits for MediaStore to scan the paths (at most 10 s, and after that it asks about the rows that exist) and then asks about the rows that are not favourites yet. So when the old row came back with its mark, nothing is asked and no dialog shows; a path with no row (a `.nomedia` folder, which MediaStore does not index) has no mark to lose and is not asked.
  - *One system request.* It is `MediaStore.createFavoriteRequest` with all the rows of the batch or the restore. It needs an Activity, so the data layer queues it in `FavoriteRequests` and `FavoriteRequestHost`, in `MainActivity`, launches the queued requests one at a time while the activity is started, on whichever screen is open. It waits for the screen to be free before it takes a request off the queue, so a rotation or Home during the wait loses nothing. A rotation brings the answer to the new activity. An activity that is finished for good (not rotating) drops the request on screen, since no answer will come, so later requests are not blocked until the process dies. The Compress page does not launch it: a restore from the trash screen needs the same launcher, and one host serves both. A batch that ends while the app is in the background or closed has its request wait in memory, and it goes out the next time the activity starts, which is usually on the Compress page where the user left it. The result and the Undo are on that page already. A killed process drops the queued request, and the copies stay without the mark; the originals in the trash still say `favorite=true`, so restoring one asks again.
  - *A decline.* The compress result says how many photos lost their favourite flag (`BatchState.Finished.favoritesLost`, a plural line under the counts). A system dialog that cannot open counts as a decline. A declined request after a restore says nothing, since the user has just chosen. Photos the user declined can be marked again in the gallery by hand.
  - The system probably grants a favourite request without a dialog, for every app: in AOSP's MediaProvider the request shows a translucent activity that returns at once. The code does not depend on it: a granted request is a granted request, and a dialog the user declines is a decline. It was not checked on the phone (§11).
- **One at a time, never during a scan.** Whatever runs the compressor (the compress screen, #286, and the background job, #287) runs one compression at a time, and never while a scan runs. A scan records files in batches, and a batch that read the original's size before the swap would write that size back over the copy's row. Two compressions at once would each read the free memory before either has decoded, so both would pass the check that only one fits. The compressor does not enforce this itself: the batch job does, and the compress screen runs every compression through it.
- **The batch job (#287).** `CompressBatch.start` takes a list of indexed paths and a level, and a WorkManager job (`CompressWorker`, unique work `compress`) compresses them one at a time, in the order given, in the foreground with a notification: "Compressing 3 of 12", the bytes saved so far, and a Cancel action. From API 35 the job runs as a `mediaProcessing` foreground service, which has a time budget of its own, so a long batch or a long pause for the heat does not use up the `dataSync` budget the scan needs (§4). Below API 35 it runs as `dataSync`, which has no budget there. `CompressBatch.state` is a `StateFlow` for the compress page: idle, waiting for a scan, running (photos done of the total, the saving so far, paused for the heat) and finished, with the result. One batch at a time: `start` refuses a second while one waits or runs. Each path is checked against the size and mtime the index holds when the batch starts, so a photo that changed since its scan is refused, and so is a path the index does not hold. Cancel lets the photo in progress finish, since the compressor cannot be interrupted, and stops before the next one: the photos done so far stay compressed and their originals stay in the trash. A cancel or a stop by the system takes the job out of the foreground while that photo finishes, so the system can kill the process in the middle of it. That leaves either a hidden copy, which the next batch discards, or a half swap, whose row the scan keeps (see the swap above). The result says how many photos were compressed, how many each refusal stopped, how many the batch did not reach, the real saving (the originals' size minus the copies'), and the originals the batch moved to the trash, those of a swap that failed halfway included. Undo for the whole batch (`CompressBatch.undo`) restores those originals through `Review.restore`, which puts each copy in the trash in its place, so nothing is deleted. It takes the same lock, so it waits while a scan or a batch runs: a restore rewrites rows a scan may be recording. The request and the result live only in memory: a process killed mid-batch drops the rest of the batch, WorkManager's rerun finds nothing to do, and the Undo is gone with the result, while the originals stay in the trash to restore from the trash screen.
- **The batch against the scan.** The job holds the scan's lock (`IndexWorker.running`) for the whole batch. A batch asked for while a scan runs waits for it, shows "Waiting for the scan to finish", and starts when it ends. A scan that starts while a batch waits or runs returns without scanning, as a nightly run does when "Scan now" is running: the nightly one is pinned to the next night (§4), and a "Scan now" is dropped, so Clean does not offer it then: its "Scan now" gives way to a line saying a compression runs. When both are asked at once, the batch wins: `start` marks the batch as waiting or running before its worker starts, and a scan checks that mark after it took the lock, so a scan that has not yet taken the lock and passed the check counts as not started. The batch goes first because the user asked for it and watches its notification, while the nightly scan comes back the next night, and a scan after a batch reads the copies, so the compress page shows them as compressed sooner. Before the first photo, holding the lock, the job discards the copies a killed compression left (`.pending-cribrum-<uuid>.jpg`, through `AppTrash.discardCopy`) in every folder that holds an indexed image, since no compression can be running then.
- **Heat.** Before each photo the job reads the thermal status and the headroom, as the scan's heat line does (§4), and while the level is severe it waits, reading again every 10 seconds, and the notification says "Paused while the phone cools down". A photo in progress is never stopped for the heat. Nothing was measured on the phone yet: how hot a batch of 200 MP photos makes it, and how long the pauses take.
- **Preview.** `Compressor.preview` runs the same decode, scale, encode, gain map checks and EXIF copy into a file the caller names, without the marker or the swap, and returns the same refusals, `NOT_SMALLER` included when the file is not smaller. It goes through the same memory check as a compression (2.5 times the decoded bitmap against `availMem − threshold`). The compress summary (§8) calls it for up to three photos, one after the other, each into its own file. It takes the compressor's own lock, so two previews do not overlap. Unlike a compression it is cancellable, since a closed summary should not leave a 200 MP decode holding the lock: it checks for cancellation between the decode, the scale and the encode (the bitmap calls themselves cannot be interrupted), recycles its bitmaps, and deletes the output through `AppTrash.discardCopy` when it refuses, fails or is cancelled, so the output is named by `copyFileFor`. The summary only opens when no batch of the screen waits or runs: the preview does not take the "never during a scan" rule's lock, because it writes nothing a scan reads, but it uses the memory of one photo at a time, and a batch is using one at the same time.
- **Refusals.** The compressor returns the copy, or one reason the compress screen (#286) words: the result is not smaller, the phone has too little free memory (an `OutOfMemoryError` included), the bitmap or the copy lost its gain map, anything else failed (a file that could not be read, written or swapped, or that changed since its scan), or the original was left in the trash. The original stays at its path in every case but one, a swap that failed halfway and could not move it back, which has its own reason: the original is in the Cribrum trash.
- **Tests for #285.** Besides the table above: all three Ultra HDR markers (`hdrgm` XMP, ISO 21496-1 APP2 and MPF APP2) survive the whole pipeline, encode, EXIF save and marker, and the gain map still decodes. A photo whose bitmap lost its gain map is refused. A faked low-memory reading refuses High quality on a large photo. Robolectric's native graphics decode no gain map and write none, so the unit tests check the bytes: the three markers survive the EXIF save and the marker, and the MPF still points at the gain map image. The encode, and the decode of the result's gain map, stay with the phone (#283 checked them on SDK 37). Every Ultra HDR photo loses its gain map in Robolectric's decoder, which is how the refusal is tested. The tests also check that MediaStore is told about the path after the rename, when the file there has the original's date taken and mtime. `DATE_TAKEN` itself needs the phone.

## 10. Python lab

Goal: prove that the detectors work on real data before writing the app.

1. **Collect:** copy the device's images to a local folder (`adb pull`, or a USB file transfer), messaging-app folders included. Image data is never committed.
2. **Detect:** implement the detectors behind the same interfaces as §7.
3. **Label:** a keyboard-driven labeling tool (`k` = keep, `d` = delete). A label carries no category: the labeler can tell what to keep, but not which detector should catch it, and asking for one turned out slow and error-prone. MobileCLIP clusters similar images so a whole cluster can be labeled at once. Target: 500–1,000 labeled images.
4. **Measure:** **recall** first, then the number of candidates it costs. The target is 95% recall on deletable images, measured for the whole library, not for the labeled sample. The sample is stratified: half of it is candidates, spread over the categories, and half is images no detector flagged, while 88% of the library were candidates when the first labels were drawn. It over-represents the images that are hardest to catch, so its recall reads lower than the library's. The evaluate report prints both. For the library, it weights each label by the size of its stratum in the index divided by the number of labels in that stratum. Each label records its stratum from now on (`candidate` or `unflagged`, `labels.sqlite` gets the column when it is opened). The 1,200 labels made before that have none, so the report places them by whether the thresholds in use when they were sampled made their image a candidate (`SAMPLING_THRESHOLDS`, the values before this change). That is an approximation, and the report says how many labels it applies to.

    | Thresholds | Sample recall (716 deletes) | Library recall | Kept images flagged (of 484) | Candidates (of 10,220) |
    |---|---|---|---|---|
    | Before | 79% (567) | 94% | 210 | 9,010 |
    | Now | 86% (615) | 96% | 219 | 9,171 |
    | Cheapest found for 95% on the sample | 96% (689) | 97% | 342 | 9,751 |

    On the sample, the 90% to 95% steps catch the last images only through `FORWARDED` at 0.45, which flags every messaging-app image and makes 95% of the library candidates. Measured on the library, the target is met with the thresholds in `ranker.py` and `Ranker.kt`. Stickers (6,306 images, 62% of the library) are always candidates, so they are more than two thirds of the candidates at any recall.

    **How the thresholds were picked.** The evaluate report prints, for each category and threshold, the labeled deletes and keeps the category flags and the ones it adds to the candidates the other categories already make. A threshold is lowered only when the images it adds to the whole candidate set are clearly more often deletes than keeps. Steps that add a handful of images are noise. The values are the maintainer's choice, read from that table:

    | Step | Deletes added | Keeps added | Candidates added |
    |---|---|---|---|
    | `DOCUMENT` 0.5 to 0.2 (applied) | 48 | 9 | 158 |
    | `DOCUMENT` 0.2 to 0.1 | 17 | 11 | 111 |
    | `BLURRY` 0.4 to 0.2 | 6 | 7 | 34 |
    | `NEAR_DUPLICATE` 0.5 to 0.3 | 3 | 6 | 33 |
    | `BAD_EXPOSURE` 0.5 to 0.4 (applied) | 0 | 0 | 0 |
    | `BAD_EXPOSURE` 0.5 to 0.1 | 1 | 0 | 5 |

    Only `DOCUMENT` clears the rule. `BAD_EXPOSURE` at 0.4 changes nothing on these labels. Every other category stays at 0.5 (`BLURRY` at 0.4). `BURST` has a small list (63 images, 10 deletes and 28 keeps), but recall comes before precision and it costs few reviews. `FORWARDED` at 0.4 would flag every messaging-app image, for 301 more deletes and 224 more keeps over 2,198 more images outside sticker folders, about the sample's base rate, so the extra images tell nothing.

    Lower thresholds also move images up the review order: the chance that a labeled delete comes before a labeled keep goes from 0.768 to 0.785.

    **Same labels.** The thresholds were picked on the same labels they are measured on. A bootstrap over the labels gives 83% to 88% for the sample recall and 95.2% to 96.6% for the library recall (95% intervals). A review of the first set of thresholds tried, which moved more thresholds and reached 90% on the sample, held out half of the labels in 20 random splits: 89.5% recall on average and 83% at worst. New labels, drawn with the recorded strata, are the check.

    The 101 deletes in the sample that no detector flags are 95 in messaging-app folders and 6 in camera folders. For all 95 of the messaging ones the closest category is `FORWARDED`. They are photos in a messaging folder that the zero-shot prompts do not read as memes or greetings, so nothing in the signals tells them from the 108 kept messaging images that are flagged. What to chase next is a signal for received photos nobody kept, not a different threshold.

    Recall of the categories on the 716 deletes, with the deletes no other category flags in brackets: `FORWARDED` 45% (32), `DOCUMENT` 43% (81), `STICKER` 33% (30), `SCREENSHOT` 15% (29), `NEAR_DUPLICATE` 16% (14), `BLURRY` 14% (6), `BAD_EXPOSURE` 12% (1), `BURST` 1% (4), `EXACT_DUPLICATE` 0.3% (0). Most deletable images are flagged by several categories, so a category's recall alone is not what it adds. The report prints both columns, so a re-run refreshes them.
5. **Freeze:** export golden fixtures (sample images with expected signals) for the Kotlin implementation's tests. The fixture images are synthetic, generated from fixed seeds (`fixtures/`), never personal photos.

## 11. Future work and open questions

- **Cloud classifiers:** a `Detector` implementation that calls a vision model API. It should be opt-in, send only downscaled thumbnails, and exclude images with faces by default.
- **Cloud libraries:** a new `ImageSource`. Since 2025 the Google Photos Library API no longer gives third-party apps read access to a user's whole library, and it never supported deletion. Cleaning Google Photos may need a different approach.
- **Play Store:** "All files access" is granted only to specific app categories. Deep scan might have to become an optional feature.
- **Desktop and iOS:** reachable through Kotlin Multiplatform / Compose Multiplatform.
- **Learning from decisions:** adjust per-category thresholds from the user's keep/trash history.
- **Recall level as a setting:** the user picks how many of the deletable images the candidates should catch, trading a longer review for fewer misses.
